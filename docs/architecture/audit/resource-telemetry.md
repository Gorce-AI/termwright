# Resource telemetry

Status: **IMPLEMENTED — EXTERNAL CERTIFICATION PENDING**

Native run manifest v8 has one required, validated resource-telemetry record.
The host measures coordinator CPU deltas, start/end RSS, a 50 ms sampled RSS
peak, PTY slot peak, journal admissions/bytes, sink batches, and peak bounded
journal backlog. Sampling starts with the synchronous run request and is always
stopped when the run completes, including failed history startup.

Every admitted attempt also samples its Vitest worker process from admission
through the public post-cleanup finalizer. The authoritative
`attempt.finished` event carries capability-qualified user/system CPU deltas
and sampled peak RSS. The host validates those untrusted worker numbers, sums
CPU across attempts, and publishes the maximum worker RSS in the run manifest.
This is explicitly worker-process evidence, not whole-process-tree evidence.

Each active trace writer emits one authoritative `trace.resource` record with
raw PTY output bytes observed, exact serialized semantic bytes and full/delta
counts, generated trace bytes, and retained final artifact bytes. The host
aggregates these records, while the run-history reader recomputes the same
totals from the independently checksummed event stream. A session without a
trace makes the session-derived totals `unavailable`, so a failed/missing
writer record can never be mistaken for zero. A run with no terminal sessions
has exact zeroes. A discarded private `retain-on-failure` spool reports
generated bytes but zero final artifact bytes.

The schema uses the literal `unavailable` where ownership or platform support
does not justify a number. It no longer exposes the misleading generic
`ownedProcessPeakRssBytes` or `ownedProcessCountPeak` fields. On Windows, the
native PTY queries the Job Object immediately before disposal and records
cumulative user/kernel time in 100 ns units, peak job memory (explicitly not
RSS), process totals, and I/O counters. Manifest aggregation states exactly
which values are sums across session jobs and which value is the maximum of
per-session peaks. The independently checksummed `session.finished` evidence is
the oracle; a missing or malformed session sample makes the run metric
`unavailable` or corrupt rather than partial.

POSIX process groups still return `unavailable`: they prove ownership and
liveness but do not provide an equivalent portable accounting object, and the
campaign deliberately does not add PID-enumeration polling. The host also does
not invent a concurrent run-wide temp-disk peak from individual writer maxima.
Zero remains meaningful only for an available counter that observed no use,
such as PTY slots in a pure unit run.

The run-history reader accepts only manifest v8. It also verifies the separate
checksummed `events.ndjson` stream; there is no older-format reader or migration
path.

Each Trace v4 writer additionally reports the exact high-water bytes in its
private staging directory, including the incomplete marker. The host does not
sum those per-writer peaks and mislabel the result as a concurrent run-wide
peak.

Remaining work is explicit: a capability-qualified POSIX process-tree collector
if a non-polling ownership-safe primitive is found, and a concurrent host-wide
temp-disk peak sampler. The Windows native query and full Node 22/24 matrix
remain external certification evidence until Windows CI executes this commit.
